Social Media Platform\
Written in Go with hybrid fan-out, replicated LSM storage (Pebble) and MySQL, and a Redis feed cache. Inspired by Twitter's architecture.

---

Opening feeds can be slow across thousands of users when searching the disk for all followees and obtaining their latest post. One way to improve feed loading is that when posts are posted, they automatically get delivered to a feed mailbox, and users who want to access their feed can quickly open the mailbox. The posts are also saved to an LSM Tree sorted by poster ID followed by time of posting, for long term storage. However, if a user has several followers, delivering to all their mailboxes can also be slow because there are so many mailboxes, and this can bottleneck other posters's feed deliveries. Thus, celebrities should be handled differently: celebrity posts are saved on the LSM Tree, and upon opening a feed, they are searched up and merged with the cache containing regular followees' posts.

The cache exists on Redis, capped at the latest 20 posts, and posting sends mail to Redis via 4 Kafka consumers. If Redis is down, feeds fetch every followee's newest post from the LSM Tree instead.

Why LSM Trees? When it comes to reading newly inserted, smaller amounts of data, both are equally fast because the data structures maintain a copy of the latest data in memory. LSM Trees are good at fast writes compared to a B-Tree when there is heavy concurrent writing load that gets bottlenecked at the disk transfer level, a common situation for a platform like Twitter. B-trees are faster when the goal is to read old data in long stretches. But feed loading fetches a single latest post for a celebrity, so the post is more likely to exist in RAM where the bottleneck goes away. This is why I think the LSM Tree is a better choice here than the B-Tree. And when looking up a specific profile to fetch old posts, the B-Tree would be faster, but this use case does not occur very frequently. Even with an LSM Tree, all posts by a user are sorted and next to each other, so profile loading is faster than a Kafka style unsorted log.

User data—accounts and follow relationships—are stored in MySQL. I used a secondary index to access followers by their followee's and vice versa quickly, at the cost of more storage and write time.

To prevent data loss, I replicated both posts and user data. The idea is that if one database dies, the others act as backups. For posts, the nodes are leaderless, and writes are always accepted. This is to prioritize posting speed, which is important to users. Each node runs as its own program and talks to the main program over gRPC. Twitter uses its own RPC framework, Finagle. As for user data, there is a reason I chose MySQL for storage. Two users should not be allowed to sign up with the same email. With a leaderless approach like the naive Cassandra INSERT, a write just goes to whatever nodes are up, with nothing stopping a second signup from claiming the same email. Even if you add a check to prevent duplicates, if one node is behind due to a previous crash and it doesn't have the updated emails, a user may send a signup request to that behind node, leading to the cluster containing the same email for two different accounts. The fix is that MySQL's comes with a feature called Group Replication, which uses Paxos, a consensus algorithm that provides strong consistency. What does this mean? Well let's look at a few facts: it contains one primary node or leader through which all writes flow. Other nodes are not allowed to accept writes with the setting `super_read_only`, which is automatically handled by group replication. This primary is the master list and contains the truth. How? MySQL guarantees that before a new primary is picked, every surviving server contains every committed signup. MySQL is configured here to not allow duplicate emails or usernames. Furthermore, a quorum is used to ensure that if a signup is written into a database, it must exist across a majority of nodes. The purpose of this is that if the primary dies, the cluster does not lose that node's data because other nodes contain the same data. Putting these facts together, the strong consistency here is preventing duplicate usernames/emails both within a single node and across multiple nodes while also ensuring that data isn't lost when the primary dies. Uber is an example of a company that uses MySQL to enforce consistency in data. The cost is two-fold: 1) availability; signups only go through if a majority of nodes are up, and 2) latency; Paxos must communicate across nodes to confirm a write and also avoids concurrent writes unlike leaderless.

To setup and run:

Install [Go](https://go.dev/dl/), Java 17+, [Redis](https://redis.io/downloads/), [MySQL 8.4](https://dev.mysql.com/downloads/mysql/), and [Kafka 4.3](https://kafka.apache.org/downloads) with their `bin` folders on your `PATH`. Then run `./start.sh` from the project folder.

To stop:
Run `./stop.sh`. Stopping does not delete the stored post and user data.
